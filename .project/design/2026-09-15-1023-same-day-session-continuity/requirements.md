# 要件定義書: ワークアウトセッションの「同じ日は同一セッション」継続化

参照: `C:\project\MuscleBoost\.project\research\topics\2026-09-15-1023-same-day-session-continuity.md`（情報収集レポート。事実関係の一次情報はすべてこちらを正とする）

## Why（背景・課題）

- 現状、`WorkoutSession`にはステータス・終了時刻の概念が存在せず（`prisma/schema.prisma:46-58`）、「セッションが切れる」という現象はDB上のライフサイクルではなく、**クライアント側の状態喪失**（ページ離脱によるReact stateのアンマウント）と、**「今どのセッションに記録中か」をサーバー側にもクライアント側にも一切覚えていないこと**が実体である（情報収集レポート確認済み）。
- ユーザーがアプリを落とす／プロフィール等の別画面に遷移してから再度「記録する」（ホーム画面「①今日の記録をする」）を選ぶと、`/workouts/new`→`createWorkoutSession`（`src/app/actions/workouts.ts:17-27`）が無条件で新規`WorkoutSession`を作成するため、同じ日であっても記録のたびにセッションが分裂する。
- 依頼の意図は「同じ日なら記録の入り口をどこから通っても、既存の当日セッションに合流し、記録が1つの塊としてまとまること」であり、認証セッション（NextAuthログイン状態）とは無関係な、ワークアウトデータのUX/設計課題である（情報収集レポートで認証系との切り分け済み）。

## What（実現すること）

1. ユーザーが記録を開始しようとしたとき、**その日（JST基準の暦日）に既に自分の`WorkoutSession`が存在すればそれを再利用し、新規セッションは作らない**。存在しなければ新規作成する（find-or-create）。
2. ホーム画面「①今日の記録をする」から記録を開始した場合、当日セッションが既にあれば入力フォームを経由せず、そのままそのセッションの詳細画面（記録追加画面）に直接到達する。
3. `/workouts/new`（実施日時・メモを指定して明示的にセッションを作る画面。`/workouts`一覧の「新規セッション」ボタン経由でも到達可能）は引き続き存在するが、指定した実施日時が既存の当日セッションと同じ暦日（JST）である場合は、新規作成せず既存セッションに合流する（フォームのメモ入力は合流時には反映されない。既存セッションのメモを維持する）。
4. セッションの結合により「セッション削除」の影響範囲（=その日の記録すべて）が実質的に拡大するため、削除操作に確認ダイアログを追加する。

## How（実現方針の概要。詳細は基本設計書・詳細設計書で確定）

- 情報収集レポートの候補比較のうち、**候補A（find-or-create方式）と候補B（「記録する」導線を当日セッションへの直行に変える）を組み合わせて採用**する。候補C（`WorkoutSession`にステータス/`closedAt`を追加し明示的な終了操作を導入する）は、スキーマ変更を伴い依頼のスコープに対して過剰であるため今回は不採用とし、将来拡張候補として設計書に記録するに留める。
- 「同じ日」の判定は`performedAt`（そのセッションが実施された日時。ユーザーが`/workouts/new`で編集可能な既存フィールド）の**JST（Asia/Tokyo, UTC+9固定・サマータイムなし）暦日**を基準とする。サーバーの実行環境（OS/Nodeプロセス）のローカルタイムゾーンや`TZ`環境変数の設定状況に依存せず、コード内で固定オフセット計算により暦日境界を求める（本番VPSのシステムタイムゾーンが未確認であるという情報収集レポートのリスクに対する直接的な対処）。
- スキーマ変更は行わない。既存の`WorkoutSession.performedAt`と`@@index([userId, performedAt])`（`prisma/schema.prisma:57`）で当日検索を実現する。

## 既存UIの事実確認（要件確定のための前提）

- コードベース全体（`src/app/**`, `src/components/**`）を確認した結果、**ユーザーがセッションを明示的に「終了する」操作は現状UIに存在しない**。存在する操作は「セッションを作成する」（`/workouts/new`）と「セッションを削除する」（`/workouts/[id]`の「セッションを削除」ボタン、`deleteWorkoutSession`）のみである。
- したがって本要件は「セッションを明示的に終了する手段を追加する」ことをスコープに含めない。**同じ日（JST暦日）の記録は、ユーザーの操作によらず常に1つの`WorkoutSession`に集約される**という仕様として確定する。1日に複数回（朝・夜など）ジムに行くユーザーも、本フェーズでは同一セッションに統合される想定とする（情報収集レポートの「推測・未確認」事項を、依頼文の「同じ日であれば同一セッションとして扱いたい」という文言に忠実に、シンプルな1日1セッションモデルとして確定する）。この前提を変更したい場合（1日複数セッションを許容したい等）は、別プロジェクトとして候補C相当の拡張を検討する。

## ユーザー要件

- UR-1: ジムでの記録中にアプリを閉じたり別画面（プロフィール等）に移動したりしても、同じ日のうちに再度「記録する」を選べば、新しいセッションではなく、それまで記録していた当日のセッションに記録を追加できる。
- UR-2: ホーム画面「①今日の記録をする」を選んだとき、その日すでに記録を始めていれば、余計な確認画面（新規作成フォーム）を経由せずに、そのままこれまでの記録が見える画面に到達する。
- UR-3: その日まだ何も記録していなければ、これまで通り新しいセッションが作られ、記録を始められる。
- UR-4: 過去の日付を指定して記録を追加したい場合（`/workouts/new`で日時を過去に変更するケース）、その日の既存セッションがあれば同様にそこへ合流し、無ければ新規作成される。
- UR-5: セッションが結合されたことで「セッションを削除する」操作がその日の記録をまとめて削除する行為になるため、誤って削除しないよう確認できる。

## システム要件

- SR-1（暦日判定関数）: `src/lib/date.ts`に、UTCの`Date`を受け取りJST暦日の開始・終了時刻（UTCの`Date`、終了は排他的境界）を返す関数`getJstDayRangeUtc(date: Date): { dayStartUtc: Date; dayEndUtc: Date }`を追加する。JST変換は固定オフセット`+9時間`（`9 * 60 * 60 * 1000`ミリ秒）をUTC時刻に加算する方式とし、`Intl`のタイムゾーンDB・外部ライブラリ・`TZ`環境変数のいずれにも依存しない（JSTはサマータイムが存在しないため固定オフセットで正確に計算できる）。
- SR-2（find-or-createロジック）: `src/app/actions/workouts.ts`の`createWorkoutSession`を変更し、入力の`performedAt`が属するJST暦日の範囲（SR-1の関数で算出）でログインユーザー自身の既存`WorkoutSession`を検索する。存在すればそのセッションを返し（新規作成しない）、存在しなければ従来通り新規作成して返す。既存セッションが複数該当する理論上のケース（本機能導入前に同日に複数作成されたレコードが既に存在する場合等）では、`createdAt`昇順で最も早く作られたものを正とする。
- SR-3（当日セッションへの直行導線）: `src/app/actions/workouts.ts`に、引数なしで「現在時刻（=今日）」を基準にSR-2のfind-or-createロジックを実行する新しいServer Action（例: `getOrCreateTodaysWorkoutSession`）を追加する。`src/app/workouts/today`に新規ページ（Server Component）を追加し、このServer Actionを呼び出した結果のセッションIDへ`redirect()`する。
- SR-4（ホーム画面の導線変更）: `src/app/page.tsx`の「①今日の記録をする」リンクの`href`を`/workouts/new`から`/workouts/today`に変更する。
- SR-5（`/workouts/new`の位置づけ維持）: `/workouts/new`（実施日時・メモを指定するフォーム画面）およびその導線（`/workouts`一覧の「新規セッション」ボタン）は削除・改廃しない。SR-2の変更により、このフォームから送信した場合も内部的にfind-or-createが働く。
- SR-6（合流時のメモ非反映の明示）: `/workouts/new`のフォーム画面に、「指定した日に既存の記録がある場合は、そちらのセッションに記録が追加されます（メモ欄の入力は反映されません）」旨の説明文を表示する。
- SR-7（削除確認）: `src/app/workouts/[id]/page.tsx`の「セッションを削除」操作に、削除前の確認ダイアログ（記録件数を含む警告文）を追加する。
- SR-8（既存集計ロジックの非変更）: `listWorkoutSessions`・`getWorkoutSession`・`getDashboardStats`（`src/app/actions/workouts.ts:240-317`）のカロリー・件数集計ロジック自体は変更しない（情報収集レポートの分析通り、対象`WorkoutSession`の粒度が変わるのみで計算式に影響はない）。
- SR-9（スキーマ非変更）: `prisma/schema.prisma`の変更・マイグレーションは行わない。

## 非機能要件

- NFR-1（タイムゾーンの一貫性）: 「同じ日」の判定基準は本番VPSのOS/Node実行環境のタイムゾーン設定に一切依存してはならない。JST固定オフセット計算をコード内に明示することで担保する。
- NFR-2（判定基準フィールドの一貫性）: 「同じ日」の判定は常に`performedAt`を基準とし、`createdAt`を基準にしない（`createdAt`は複数該当時のタイブレークにのみ用いる）。
- NFR-3（後方互換性）: `createWorkoutSession`の入力契約（`workoutSessionInputSchema`: `performedAt`必須・`memo`任意）は変更しない。戻り値の型に`reused: boolean`を追加するが、既存の呼び出し元（`/workouts/new/page.tsx`）は`data.id`のみを参照しているため後方互換である。
- NFR-4（性能）: find-or-createに伴い追加されるクエリは`WorkoutSession`に対する`userId`+`performedAt`範囲検索1回のみであり、既存インデックス（`@@index([userId, performedAt])`）で処理される。既存の体感速度に有意な影響を与えない。
- NFR-5（同時実行の残余リスクの許容）: 同一ユーザーが極めて短時間に複数タブ等で同時に「記録を始める」を実行した場合、find-or-createのcheck-then-actの間に競合し、まれに同日セッションが2件作成される可能性がある。スキーマにユニーク制約を追加しない（NFR-9で非破壊変更方針を優先する）ため、既存の送信中はボタンを無効化するUI（`/workouts/new/page.tsx`の`submitting`状態）による低減に留め、残余リスクとして許容する。
- NFR-6（既存E2Eテストへの影響確認）: `tests/e2e/workout-flow.spec.ts`の`createSession()`ヘルパーおよびそれを用いる全テストケースが、find-or-create方式変更後も成功することをQAフェーズで検証する。

## 受け入れ条件（Acceptance Criteria）

- AC-1: 当日、既に`WorkoutSession`を1件以上持つユーザーが、ホーム画面「①今日の記録をする」を選ぶと、新規セッションが作られず、既存の当日セッション詳細画面（記録が閲覧・追加できる画面）に直接遷移する。
- AC-2: 当日まだ`WorkoutSession`を持たないユーザーが、ホーム画面「①今日の記録をする」を選ぶと、新規セッションが1件作成され、その詳細画面に遷移する。
- AC-3: `/workouts/new`から実施日時を「今日」のままセッション作成を送信すると、AC-1・AC-2と同じくfind-or-createが働く（新規フォームを経由してもセッションが二重に作られない）。
- AC-4: `/workouts/new`から実施日時を「当日セッションが存在しない過去の日付」に変更して送信すると、その日付で新規セッションが作成される。
- AC-5: `/workouts/new`から実施日時を「既に自分の`WorkoutSession`が存在する過去の日付」に変更して送信すると、新規作成されず既存セッションに合流し、送信したメモは反映されない（既存セッションのメモが維持される）。
- AC-6: 日付境界（JST 0:00）をまたぐ実施日時（例: UTCで前日15:00ちょうど＝JST当日0:00、UTCで前日14:59:59＝JST前日23:59:59）で判定した場合、境界を挟んで別々の日と正しく判定される。
- AC-7: 「セッションを削除」操作時に確認ダイアログが表示され、キャンセルすると削除が実行されない。
- AC-8: 既存のカロリー・トレーニングボリューム・ダッシュボード集計（`/workouts`一覧、セッション詳細画面）が、セッション統合後も正しい合計値を表示する。
- AC-9: `npm run test:e2e`（Playwright）が全て成功する。
- AC-10: `npm run test`（Vitest）が全て成功する（新規追加するJST暦日境界の単体テストを含む）。
- AC-11: `npm run build`（型チェック含む）がエラーなく成功する。
