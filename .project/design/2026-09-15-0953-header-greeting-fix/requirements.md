# 要件定義書: ヘッダーの不要な「〇〇さん」表記の削除とトップ画面挨拶文へのユーザー名付与

参照: `C:\project\MuscleBoost\.project\research\topics\2026-09-15-0953-header-greeting-fix.md`（情報収集レポート。事実関係の一次情報はすべてこちらを正とする）

## Why（背景・課題）
- ログイン後の全画面共通ヘッダー（`src/components/Header.tsx`）に表示されている `{userName} さん` は、`href`も`onClick`も持たない素の`<span>`であり、同じナビ行に並ぶ「記録」「マシン」「プロフィール」「ログアウト」と見た目上区別がつかないため、ユーザーには「クリックできそうなのに反応しない要素」として認識され、UI上浮いて見える。
- 一方でトップ画面（`src/app/page.tsx`）の見出し「今日は何をしますか？」は無機質であり、ここにユーザー名を出す方が自然な導線になる。
- 依頼の意図は「意味を持たないラベルを削除し、ユーザー名という情報自体は、より自然な場所（挨拶文）に移設して活用する」こと。単なる削除ではなく、情報の再配置である。

## What（実現すること）
1. ヘッダーから `{userName} さん` の表示を削除する。ヘッダーのその他の要素（ナビリンク、ログアウトボタン、未ログイン時のログイン/登録リンク分岐）は現状維持する。
2. トップ画面の見出しを「今日は何をしますか？」から「〇〇さん、今日は何をしますか？」に変更する。〇〇には、ログイン中のユーザーの実名（`User.name`）を最新のDB値で表示する。

## How（実現方針の概要。詳細は基本設計書・詳細設計書で確定）
- トップ画面（`src/app/page.tsx`）を非同期コンポーネント化し、`getCurrentUserOrThrow()` でログインユーザーIDを取得した上で `prisma.user.findUnique` によりDBから最新の `name` を取得し、見出しに埋め込む。
- ヘッダー（`src/components/Header.tsx`）は該当の`<span>`表示行のみを削除し、`userName` propおよびログイン判定分岐（`userName ? ... : ...`）は維持する。

## ユーザー要件
- UR-1: ログイン後にヘッダーを見たとき、クリックできない「〇〇さん」というラベルが目に入らないこと。
- UR-2: ログイン後のトップ画面を開いたとき、見出しに自分の名前が入った挨拶文「〇〇さん、今日は何をしますか？」が表示されること。
- UR-3: プロフィール画面で表示名を変更した場合、その後にトップ画面を開き直したときは変更後の名前が挨拶文に反映されること（ログアウト・再ログインを要求しない）。

## システム要件
- SR-1: `src/components/Header.tsx` の `<span className="text-gray-500">{userName} さん</span>`（既存26行目）を削除する。`HeaderProps`（`userName: string | null`）およびログイン判定の三項分岐構造は変更しない。
- SR-2: `src/app/page.tsx` の `TopPage` を `async function` に変更し、コンポーネント内で認証済みユーザーの `name` を取得する。取得方式は「プロフィール画面（`src/app/profile/page.tsx`）と同一パターン」＝ `getCurrentUserOrThrow()` でユーザーIDを取得後、`prisma.user.findUnique({ where: { id } })` でDBから直接 `name` を取得する方式を採用する（採用理由は基本設計書「アーキテクチャ判断」参照）。
- SR-3: 見出し文言は既存の末尾「？」を維持し、`「${name}さん、今日は何をしますか？」` の形式とする（依頼文の表記ゆれより既存実装の文言トーンを優先する）。
- SR-4: `name` が取得できない・空文字のケース（DBスキーマ上は必須列だが、防御的に考慮する）では、名前部分を省略し既存の「今日は何をしますか？」のみを表示する（クラッシュさせない）。
- SR-5: `/` は `middleware.ts` により未ログインではアクセス不可のため、`TopPage` 内で未ログイン状態を通常時に想定する必要はないが、`getCurrentUserOrThrow()` が `UnauthorizedError` を投げた場合にNext.jsの標準エラー処理（例外伝播）に委ねる形で問題ないことを確認する（詳細設計書「エラー処理方針」参照）。

## 非機能要件
- NFR-1（一貫性）: ユーザー名取得はプロフィール画面と同じ「DB直読み」パターンに統一し、コードベース内の実装パターンを分散させない。
- NFR-2（性能）: トップ画面へのDBアクセス追加は1クエリ（`prisma.user.findUnique`、主キー検索）のみとし、既存の軽量な静的ページの体感速度に有意な影響を与えない。
- NFR-3（後方互換）: `Header` コンポーネントの `props` インターフェース（`HeaderProps`）は変更しない。`Header` を利用する他画面（`layout.tsx`）への影響を出さない。
- NFR-4（テスト整合性）: 既存E2Eテスト `tests/e2e/auth.spec.ts` 内の見出しテキストに対する厳密一致アサーション（18行目 `getByRole("heading", { name: "今日は何をしますか？" })`）は本変更で必ず失敗するため、本プロジェクトのスコープ内でテストコードも合わせて更新する。

## 受け入れ条件（Acceptance Criteria）
- AC-1: ログイン後、いずれの画面でもヘッダー内に「〇〇さん」という文言（クリック不可のラベル）が表示されない。
- AC-2: ログイン後にトップ画面（`/`）を開くと、見出しが「〇〇さん、今日は何をしますか？」（〇〇はログイン中ユーザーの実名）と表示される。
- AC-3: プロフィール画面で表示名を変更して保存した直後、再度トップ画面（`/`）を開くと、変更後の新しい名前が見出しに反映される（再ログイン不要）。
- AC-4: ヘッダーの他の要素（記録／マシン／プロフィールへの`Link`、ログアウトボタン、未ログイン時のログイン/登録リンク）の表示・動作に変化がない。
- AC-5: `npm run test:e2e`（Playwright）が全て成功する（`auth.spec.ts` の文言アサーション更新を含む）。
- AC-6: `npm run build`（型チェック含む）がエラーなく成功する。
