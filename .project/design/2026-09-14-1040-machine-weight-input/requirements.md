# 要件定義書: マシン選択肢の統一と重量記録欄の新設（MuscleBoost）

## 0. 参照

- 対象リポジトリ: `C:\project\MuscleBoost`
- 本書は Why → What → How の順で記述する。How の詳細（アーキテクチャ・DB方針）は `basic-design.md`、実装粒度の詳細は `detailed-design.md` に譲る。

## 1. Why（背景・目的）

- 現状、マシン選択プルダウン（`ExercisePicker.tsx`）は「マシン名 × 強度レベル（軽度/中等度/高強度）」の組み合わせでレコード化された `Exercise` を選択肢にしており、同じマシンなのに3つの選択肢が並ぶ（例:「チェストプレス（軽度）」「チェストプレス（中等度）」「チェストプレス（高強度）」）。ユーザーにとって「どれを選べばいいか分かりにくい」「マシンを探す手間が増える」という体験上の課題がある。
- 一方で、実際にどれくらいの重さ（バーベル・ダンベル・マシンの設定重量）でトレーニングしたかを記録したいという需要があるが、現状その入力欄が存在しない。
- ユーザーからは「1マシン=1選択肢にしてほしい」「代わりに重さの入力欄が欲しい（KG/ポンド切り替え可能）」という具体的な要望があり、かつ **重さの値をカロリー計算に使わないこと、既存のMET値ベースのカロリー計算式・ロジックを変更しないこと** が確認済みの制約として与えられている。

## 2. What（ユーザー要件）

### 2.1 ユーザーストーリー
1. ユーザーとして、マシンを選ぶときに同じマシン名が強度違いで複数出てくるのをやめてほしい。1マシン名につき1つの選択肢だけを見たい。
2. ユーザーとして、トレーニング記録をつける際に「今日は何kg（または何ポンド）でやったか」を記録したい。単位はKGとポンドを切り替えられるようにしてほしい。
3. ユーザーとして、記録した重さは一覧・詳細画面で確認できるようにしてほしい。
4. ユーザーとして、重さを入力してもしなくても記録を保存できるようにしてほしい（任意入力）。
5. ユーザーとして、これまで通りセット数・レップ数・運動時間・体重（上書き）からカロリーが自動計算される体験は変わらないでほしい。
6. ユーザー（自分専用マシンを登録する側）として、マイマシン作成フォームの項目が、マスタのマシン選択に対して不整合にならないようにしてほしい（強度概念がマスタから無くなるなら、作成フォームも一貫した形にしてほしい）。

### 2.2 対象外（今回のスコープ外）
- 重さの値をカロリー計算式に組み込むこと（明示的に禁止された制約）。
- 有酸素マシン（エアロバイク・トレッドミル等）の名称整理（研究フェーズの確認により、有酸素6機種は元々1マシン1エントリに近い個別命名であり、「1マシン×強度の組み合わせ」問題の対象外）。
- ウェアラブル連携等、本要望と無関係な既存スコープ外事項。
- 単位換算の自動計算（KG⇔ポンドの相互変換機能）。本要望は「記録用（保存・表示）のみ」であり、入力された値をそのまま保存・表示する（詳細は `basic-design.md` §3、`detailed-design.md` 参照）。

## 3. システム要件（機能要件）

| ID | 要件 |
|---|---|
| FR-1 | マシンマスタ（`Exercise`）は1マシン名につき1レコードのみとする。強度レベル（LIGHT/MODERATE/VIGOROUS/HIGH_INTENSITY）による選択肢の分岐を廃止する。 |
| FR-2 | マシン選択プルダウン（`ExercisePicker.tsx`）は統合後のマスタをそのまま表示し、同一マシン名の重複選択肢が発生しないようにする。 |
| FR-3 | トレーニング記録（`WorkoutLog`）に、重さの値（数値）と単位（KG/ポンド）を保存できるフィールドを新設する。両方とも任意入力（未入力可）とする。 |
| FR-4 | 記録作成フォーム（`WorkoutLogForm.tsx`）に、重さの数値入力欄と単位（KG/ポンド）切り替えUIを新設する。 |
| FR-5 | 記録一覧・詳細表示（`WorkoutLogItem.tsx` 等）で、入力された重さと単位を表示する。未入力の場合は何も表示しない（既存の `bodyWeightKgOverride` 表示パターンに倣う）。 |
| FR-6 | カロリー計算ロジック（`src/lib/calorie.ts`、`calculateCalories`関数のシグネチャ・実装）は変更しない。重さフィールドの値はカロリー計算のいかなる入力にもならない。 |
| FR-7 | 既存の `WorkoutLog` データについて、統合によって削除されるマシン（強度違いの重複）を参照している記録の `exerciseId` を、統合後の代表マシンへ矛盾なく再ポイントする。過去記録のカロリー表示・MET値表示（`metValueSnapshot`, `caloriesBurned`）は変更前の値のまま保持される。 |
| FR-8 | マイマシン作成フォーム（`ExerciseForm.tsx`）・関連バリデーション（`exerciseInputSchema`）から強度選択欄を削除し、マスタ側の仕様と一貫させる（FR-1に伴う必然的な追随変更）。 |

## 4. 非機能要件

| ID | 要件 |
|---|---|
| NFR-1 | 本番Turso DBに対するスキーマ変更は、既存ユーザーの記録データを一切破損・消失させない（`WorkoutLog` の行自体は削除しない。カロリー関連スナップショット値は不変）。 |
| NFR-2 | マイグレーション適用手順（`prisma migrate deploy` を含む）をデプロイフローに明記し、コードデプロイとDBスキーマ変更の間で本番エラーが発生する期間を最小化する。 |
| NFR-3 | 既存の命名規則・コーディングパターン（`as const` 配列 + Zod `enum` + `Record` ラベルパターン、Server Action の `ActionResult` 戻り値パターン）を踏襲する。 |
| NFR-4 | 既存のE2Eテスト（`tests/e2e/workout-flow.spec.ts`）が新しいマシン名・新しい代表MET値に対応した形で全件パスする状態を維持する。 |
| NFR-5 | 単位変換（KG⇔ポンド）は行わない。表示は入力時の単位のまま行い、丸め誤差によるズレを発生させない。 |

## 5. 制約・前提（確認済み）

- 重さの値はカロリー計算には一切使わない。記録用（保存・表示）のみ。
- 既存のMET値ベースのカロリー計算式・ロジック（`src/lib/calorie.ts`）は変更しない。
- `WorkoutLog.exerciseId` は `onDelete: Restrict` のFK制約を持つため、マシン統合で削除されるレコードを参照する既存行は、削除前に再ポイントが必須（技術的制約）。
- デプロイパイプライン（`.github/workflows/deploy.yml`）には `prisma migrate deploy` ステップが存在しないため、本番Turso DBへのスキーマ反映は別途手順化が必要（技術的制約、前回プロジェクトから継続する既知の申し送り事項）。
- 有酸素マシン6件は統合対象外（既に1マシン1エントリ）。統合対象は筋トレマシン10種のみ。

## 6. 受け入れ条件（Acceptance Criteria）

- [ ] マシン選択プルダウンに、同一マシン名が複数回表示されない（統合対象の筋トレ10種がそれぞれ1件ずつ表示される）。
- [ ] トレーニング記録作成フォームに、重さの数値入力欄とKG/ポンド切り替えUIが表示される。
- [ ] 重さを入力して記録を保存すると、一覧・詳細画面に入力した値と単位がそのまま（換算されずに）表示される。
- [ ] 重さを入力せずに記録を保存できる（必須ではない）。
- [ ] 重さの値を変えても、表示される消費カロリー（`caloriesBurned`）は変化しない。
- [ ] 統合前に登録されていた既存の `WorkoutLog`（強度違いレコードを参照していたもの）が、マイグレーション後も一覧・詳細画面でエラーなく表示され、カロリー値も変化していない。
- [ ] マイマシン作成フォームから強度選択欄が無くなり、他項目（マシン名・部位・MET値・説明）のみで作成できる。
- [ ] `npx tsc --noEmit` がエラー0件で通る。
- [ ] `npm run test`（Vitest, `tests/unit/calorie.test.ts`）が全件パスする（無改修で通ること自体が確認項目）。
- [ ] `npx playwright test`（`tests/e2e/workout-flow.spec.ts` 含む）が全件パスする。
- [ ] 本番Turso DBへの `prisma migrate deploy` 実行手順が設計書に明記されている。
