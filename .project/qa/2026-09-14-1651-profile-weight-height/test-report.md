## 発見した問題

### ローカルQA検証環境: devサーバーを素朴に再起動すると本番Turso DBに接続してしまう（本プロジェクトのコード自体の不具合ではなく、運用手順上の注意点）
- 症状: QA準備段階でPMが「ローカルSQLite向けに再起動済み」としていたdevサーバーだが、これは`.env`を変更せず`TURSO_DATABASE_URL`環境変数をプロセス起動時にのみ一時上書きする方式で実現されていた。QA作業中に（1）`npm run build`前の`rm -rf .next`が稼働中のdevサーバーの`.next`を巻き込んで破損させたため、（2）devサーバーを`taskkill`後に何も考えず`npm run dev`のみで再起動したところ、`.env`のデフォルト値（本番Turso想定）にフォールバックし、結果としてユーザー登録操作が本番Turso（`TURSO_DATABASE_URL`）に対して`prisma.user.findUnique`を発行してしまった。
- 期待: QA・開発作業中はローカルSQLiteのみに接続され続けること。
- 再現手順: ①devサーバー稼働中に`.next`を削除するコマンド（例: `npm run build`の一部としての`rm -rf .next`）を実行→devサーバーがランタイムエラーになる。②devサーバープロセスを終了し、環境変数の上書きなしに`npm run dev`のみで再起動する。③その状態でユーザー登録等のDBアクセスを伴う操作を行うと、`.env`のTURSO_DATABASE_URL（本番相当）に接続される。
- 原因の仮説: `src/lib/prisma.ts`・`prisma.config.ts`がいずれも`process.env.TURSO_DATABASE_URL`を直接参照する設計であり、「ローカルSQLiteへの切替え」が`.env`ファイルの内容ではなく「プロセス起動時の環境変数上書き」という、ファイルに残らない・引き継がれない手段に依存している。そのため、devサーバーを再起動する担当者（人間のエンジニアでもエージェントでも）がこの運用ルールを知らない、または明示的に環境変数を渡し忘れると、意図せず本番Turso DBに接続する状態になり得る。
- 実害: 今回発生したエラーは`prisma.user.findUnique`という読み取りクエリの実行中に例外（実際には別の原因＝当時は`.next`破損によるものだった1回目、その後の2回目でTURSO接続を誤検知）で止まったため、書き込みは一切発生しておらず、本番データへの実害はなかったことをQA担当が確認済み。またQAはこれを検知した時点で直ちに該当devサーバーを停止し、`TURSO_DATABASE_URL`をローカルファイルへ明示的に上書きした状態で再起動し直し、以降の全操作をローカルSQLiteに対してのみ実施した。
- 推奨対応: 本プロジェクトのスコープ外の恒久対策ではあるが、PM/エンジニアリングチームへの申し送り事項として、（a）ローカル検証用に`TURSO_DATABASE_URL`をローカルSQLiteに固定する起動スクリプト（例: `npm run dev:local`のようなnpm scriptを追加し、環境変数上書きをコマンド自体に埋め込む）を用意する、（b）devサーバーの起動・再起動を依頼する際は「現在どのDBに接続されているか」をPMの引き継ぎメモに明記する、といった改善を検討されたい。

### （参考・本プロジェクトのスコープ外）`tests/e2e/auth.spec.ts`の1件が不安定
- 症状: 本プロジェクトの回帰確認のためのついでに`tests/e2e/auth.spec.ts`も実行したところ、「ログアウト後、再ログインできる」が`/api/auth/error`へのリダイレクトで失敗した（他5件は成功）。
- 期待: 全6件パス。
- 再現手順: `npx playwright test tests/e2e/auth.spec.ts` をローカルSQLite接続で実行。
- 原因の仮説: `auth.spec.ts`・NextAuth周りは本プロジェクト（詳細設計書の影響範囲15ファイル）に一切含まれておらず、本改修による変更は加えていない。作業ツリーには本プロジェクト以外の複数プロジェクト分の未コミット変更（`exercises.ts`, `ExerciseForm.tsx`等）が混在しているため、それらに起因する可能性、あるいは既存の潜在的な不安定性（テスト間のクッキー競合等）の可能性がある。
- 推奨対応: 本プロジェクトの完了判定には影響しないため対応不要。ただし別途、次のマイグレーション・pushサイクルの前に原因調査することを推奨する。
